# 多機快速練習環境、審核與生命週期設計

- 日期：2026-08-26
- 狀態：設計基準；2026-08-27 已完成第一階段實作，最新完成度、流程與缺口請見 [2026-08-27-multi-machine-environment-latest-status.md](./2026-08-27-multi-machine-environment-latest-status.md)
- 適用範圍：學生快速練習、教師／官方發布、多機環境、教學檔案與腳本、容量治理、三小時回收

## 一、背景與重新定義

目前所稱的「快速模板」已不再是過去單純讓學生複製一台 VM／LXC 的功能，而是由官方或教師預先建立、可立即啟動的完整練習環境。

一個練習環境可以包含一至三台機器，例如：

```text
快速練習環境
├─ 操作主機
├─ n8n
├─ Database
└─ 教學文件、範例與操作腳本
```

學生選擇練習環境後，系統應一次配置整組機器，不需逐次人工審核；所有機器共用三小時期限，到期後整組停止並回收。

因此，產品與程式內部不宜繼續把這項功能視為單一 `VMTemplate`。建議使用以下概念：

- `VMTemplate`：一台底層 VM／LXC 的不可變母機映像。
- `PracticeBlueprintVersion`：一至三台機器、拓樸、規格和教學內容的版本化藍圖。
- `PracticeOffering`：官方或教師發布給特定對象使用的練習項目。
- `PracticeSession`：某位學生實際啟動的一組三小時練習環境。

前端名稱建議使用「快速練習」或「即時實驗環境」，避免學生把它理解成可以自由複製及永久持有的機器模板。

## 二、核心產品原則

### 2.1 學生啟動維持免審核

學生每次開始快速練習時不應等待管理員審核。人工審核應放在教師發布練習版本時，而不是放在每次學生啟動時。

原因如下：

- 快速練習的核心價值是點選後立即取得環境。
- 相同版本若已通過資源及安全檢查，沒有必要對每位學生重複審核。
- 每次啟動都審核會造成等待、管理負擔及課堂中斷。
- 容量風險可以用發布額度、最大並行數和 practice quota pool 控制。

### 2.2 指定誰能用不等於容量審核

教師指定班級或學生只能解決使用權問題，不能單獨解決容量問題。

例如，一組環境包含三台機器，每組需要 6 vCPU、8 GB RAM 和 3 個 IP。即使教師只指定自己的 40 位學生，若 40 人同時啟動，仍可能需要：

```text
240 vCPU
320 GB RAM
120 個 IP
```

因此必須同時具備兩道控制：

1. **使用權控制**：哪些班級或學生可以看到並啟動。
2. **資源治理**：每組規格、最大並行 Session、總容量及是否需要管理員審核。

### 2.3 模板描述環境，使用入口決定生命週期

底層母機模板只描述作業系統、軟體與預設設定，不應自行決定使用期限、配額和審核規則。

同一個 PostgreSQL 或 n8n 母機可以被不同流程引用：

| 使用入口 | 使用期限 | 配額來源 | 審核方式 |
| --- | --- | --- | --- |
| 快速練習 | 固定三小時 | practice pool | 學生啟動免審核 |
| 正式班級 | 班級期間及每週課表 | class pool | 班級容量審核 |
| 個人研究 | 核准的申請期間 | personal pool | 個別申請審核 |

## 三、發布與審核策略

### 3.1 建議採用一次性版本審核

| 建立者及內容 | 建議結果 |
| --- | --- |
| 管理員／官方建立 | 視為已審核，可直接發布 |
| 教師建立且在安全額度內 | 自動通過並發布 |
| 教師建立但超過資源額度 | 管理員審核該版本一次 |
| 使用 GPU、特權 LXC 或特殊網路能力 | 必須由管理員審核 |
| 自動執行高權限或未受限制的腳本 | 必須安全審核或禁止發布 |

教師修改以下任何項目時，必須產生新版本並重新判定是否需要審核：

- 增減機器節點。
- 調整 CPU、RAM、Disk 或 GPU。
- 更換底層 VMTemplate。
- 修改網路拓樸或公開連接埠。
- 修改會自動執行的初始化腳本。
- 更換教學內容套件版本。

已發布版本必須保持不可變，不能因教師後續編輯而影響正在使用或已排定的 Session。

### 3.2 安全額度應由系統設定

第一版可提供可調整的預設安全額度，例如：

```text
每組最多 3 台
整組 CPU 不超過 4～6 vCPU
整組 RAM 不超過 8 GB
禁止 GPU
禁止特權 LXC
禁止未確認的公開連接埠
禁止任意 root startup script
```

實際數值應由管理者依叢集容量調整，不應散落或寫死在前端。

### 3.3 審核容量看的是最壞並行需求

審核不能只看單一學生一組環境的規格，應計算：

```text
核准容量 = 每組總需求 × max_concurrent_sessions
```

每個 PracticeOffering 至少應設定：

- `max_concurrent_sessions`：同時最多啟動幾組。
- `max_active_per_user`：預設每位學生同時一組。
- `max_sessions_per_user_per_24h`：預設每日三組或由政策調整。
- `audience_scope`：官方、全校、班級或指定使用者。
- `quota_pool`：固定使用 practice pool。

教師可以指定很多學生有使用資格，但實際並行數仍由容量額度控制。額滿時應排隊或清楚顯示稍後再試，不能部分建立。

## 四、多機 Practice Session

### 4.1 資料模型

建議建立以下核心資料：

```text
PracticeOffering
├─ id
├─ owner_id
├─ blueprint_version_id
├─ audience_scope
├─ publication_status
├─ review_status
├─ max_concurrent_sessions
├─ resource_profile
├─ content_bundle_version_id
└─ created_at / published_at

PracticeSession
├─ id
├─ offering_id
├─ user_id
├─ status
├─ starts_at
├─ expires_at
├─ stop_at
├─ reclaim_after
├─ quota_pool = practice
└─ created_at

PracticeSessionMachine
├─ session_id
├─ machine_node_id
├─ node_key
├─ role
├─ resource_vmid
├─ status
└─ error
```

若系統後續建立通用 `ResourceAllocation`，每個 SessionMachine 應再連結對應 Allocation；Session 則作為多機器的聚合單位。

### 4.2 使用次數按 Session 計算

一組三台機器必須視為一次練習：

- 同時最多一組，是一個 PracticeSession，不是一台 VM。
- 每日最多三次，是三個 PracticeSession，不是三台機器。
- CPU、RAM、Disk 和 IP 配額以整組合計。
- 三台機器共用相同 `starts_at` 和 `expires_at`。
- 回收、錯誤修復及稽核均以 Session 聚合呈現。

現有以單筆 VMRequest 計算快速模板數量的方式，不足以直接支援多機環境，必須先加入 Session 父層。

### 4.3 全有或全無

學生啟動前，系統應在同一個協調流程預留全部資源：

1. 驗證 Offering 已發布、版本可用且學生具有使用權。
2. 檢查學生是否已有進行中的 PracticeSession。
3. 檢查每日次數和 Offering 最大並行數。
4. 計算整組 CPU、RAM、Disk、GPU 和 IP。
5. 原子化預留整組容量和所有 IP。
6. 建立 Session 及所有 Machine 工作。
7. 依拓樸建立並設定機器。
8. 全部成功後將 Session 標記為 `ready`。

若整組容量不足，不應只建立其中一台或兩台。若建立中部分失敗，系統應：

- 冪等重試失敗節點，不重複建立成功節點；或
- 在無法修復時回收整組並釋放全部預留。

### 4.4 學生 API 保持簡單

建議學生只呼叫：

```http
POST /api/v1/practice-offerings/{offering_id}/sessions
```

請求內容只允許低風險資料，例如顯示名稱。學生不得自行提交：

- CPU、RAM、Disk 或 GPU。
- 底層 PVE VMID。
- `starts_at` 或 `expires_at`。
- 是否需要審核。
- 公開連接埠或特權模式。

所有規格與期限都由已發布的 Offering 版本和伺服器端政策決定。

## 五、三小時排程不是隱藏規則

快速練習仍維持固定三小時，不提供學生自行選擇開始與結束時間，也不開放自行延長。

但「不讓學生編輯」不等於「不讓學生知道」。建立前應明確顯示：

```text
立即建立
可使用 3 小時
預計於 18:30 自動停止
停止後進入回收緩衝，之後整組刪除
不可自行延長
```

建立後所有頁面應使用後端回傳的權威欄位：

- `starts_at`
- `expires_at`
- `auto_stop_at`
- `reclaim_after`
- `remaining_seconds`
- `can_extend`
- `policy_label`

前端不得自行用目前時間加三小時推算，也不得用只有日期精度的 `expiry_date` 代表三小時 Session。

建議生命週期如下：

```text
學生啟動
→ 三小時計時
→ 到期前 30 分鐘提醒
→ 到期前 10 分鐘再次提醒
→ expires_at 到達後停止整組機器
→ 進入 15～30 分鐘回收緩衝
→ 收集已設定的成果
→ 刪除整組機器
→ 釋放 IP 與 practice pool 容量
→ Session 標記 reclaimed
```

回收緩衝不是延長使用時間。緩衝期間學生不能繼續操作，只供成果收集、取消錯誤刪除或系統重試。

## 六、教學檔案與操作腳本

### 6.1 權威副本不能只存在機器內

即使母機映像內預先包含教學檔案，平台仍應在 VM 外保存權威副本，例如：

- Object Storage。
- Git repository。
- 平台管理的 Content Bundle。

PracticeBlueprintVersion 應固定引用：

```text
content_bundle_id
content_bundle_version
checksum
每個檔案的 target_node_key
每個檔案的 target_path
```

啟動 Session 時，系統依固定版本把檔案派送至操作主機、n8n 或 Database 節點。映像內可以保留相同版本作為離線備援，但不能成為唯一副本。

修改教學內容時建立新 Content Bundle 版本，不直接覆蓋已發布 Offering 所引用的版本。

### 6.2 學生資料分成暫存與成果

三小時後可以刪除的資料：

- 套件快取。
- 臨時測試資料。
- 不需繳交的機器狀態。

必須保存到 VM 外的資料：

- 作答結果。
- n8n workflow 匯出。
- SQL／資料庫 dump。
- 指定設定檔。
- 報告、程式碼或教師要求的輸出。
- AI Check 結果及教師評分紀錄。

平台應提供「提交成果」或「匯出工作區」，也可以在到期前自動收集指定路徑。教師查看的是平台保存的提交，不依賴已被回收的學生機器。

### 6.3 自動執行腳本的安全邊界

Markdown、PDF、範例 SQL 和不自動執行的程式碼可依一般教學內容處理。

以下腳本不能只因上傳者是教師就自動信任：

- 以 root 自動執行。
- 修改網路、防火牆或系統帳號。
- 下載並執行外部內容。
- 讀取 Token、SSH Key 或其他憑證。
- 建立公開服務或變更宿主機設定。

這類能力應採以下其中一種方式：

1. 使用平台允許的宣告式初始化動作及白名單。
2. 在受限 Guest 內執行，限制網路、時間與可用憑證。
3. 對高權限腳本版本進行管理員安全審核。

## 七、刪除問題與恢復策略

「腳本機／範本機被刪除」可能代表不同情境，需分別處理。

### 7.1 學生的三小時練習機被回收

這是正常生命週期。練習機本身可以被刪除，但必須先確保：

- 教學檔案的權威版本不在該機器內。
- 學生必須保存的成果已提交或匯出。
- 到期提醒清楚顯示。
- 回收工作可重試且不會重複刪除。
- Session 歷史、使用時間、錯誤與提交紀錄仍可查詢。

不建議替所有三小時練習機永久保存快照，否則會抵銷自動回收節省容量的目的。

### 7.2 學生誤按提前歸還

學生不應取得底層單台機器的刪除權限。只能操作整個 PracticeSession 的「結束練習」。

建議流程：

```text
學生確認結束
→ 立即停止 Session
→ 顯示短暫可撤銷狀態
→ 緩衝時間結束後整組刪除
```

若不提供撤銷，也至少要二次確認並明確告知未提交資料會消失。

### 7.3 已發布的母模板被教師刪除

已發布版本引用的底層 VMTemplate 必須不可變，並使用狀態機管理：

```text
draft
→ pending_review
→ published
→ deprecated
→ retired
```

規則如下：

- 被已發布 Blueprint／Offering 引用時，hard delete 回應 409。
- 有進行中 Session 時，只能標記 deprecated，不能刪除。
- deprecated 後禁止新 Session，但現有 Session 可完成。
- 所有 Session 結束且沒有任何版本引用後，背景垃圾回收才可刪除。
- 教師刪除的是草稿或未引用版本，不是正在服務學生的 golden image。

### 7.4 PVE 端母模板被意外刪除

平台需要定期對帳：

- 檢查已發布版本引用的 PVE template 是否存在。
- 遺失時將版本標記為 `unavailable` 或 `degraded`。
- 立即禁止新 Session。
- 通知管理員及 Offering 擁有者。
- 從 PBS、備份儲存或 golden image 匯出檔恢復。
- 不自動偷換到另一個模板版本，避免不同學生取得不一致環境。

若使用 linked clone，母模板在任何子機存在期間都不得刪除。若希望降低母模板消失對既有 Session 的影響，可以對重要版本使用 full clone；代價是建立時間與儲存用量較高。

### 7.5 操作／腳本專用節點建立失敗或被刪除

若多機環境中的某一台是操作主機或腳本執行節點，它仍是 PracticeSessionMachine，不應被當成特殊的永久資料來源。

處理方式：

- 腳本及教學內容從外部 Content Bundle 重新派送。
- 依固定 node key、模板版本及網路拓樸重建該節點。
- 重建前驗證同一 Session 沒有已存在的有效 VM，避免重複建機。
- 如果無法維持拓樸一致，將整個 Session 標記為 failed 並提供整組重建。
- 學生已提交成果不受節點重建影響。

## 八、可見範圍與使用授權

PracticeOffering 建議支援：

| 範圍 | 說明 |
| --- | --- |
| `system` | 官方提供，全校可見 |
| `campus` | 教師發布至全校，可能需要管理員審核 |
| `class` | 只給指定 TeachingClass 成員 |
| `users` | 只給指定學生 |
| `private` | 僅建立者測試，不對學生發布 |

學生啟動時必須由後端重新驗證：

- Offering 仍為 published。
- Blueprint 版本及所有底層 VMTemplate 都可用。
- 學生仍在 audience 中。
- 班級範圍時，學生名單仍為 active。
- 目前沒有進行中的 Session。
- 每日次數、並行數及 practice pool 仍有額度。

前端隱藏卡片只能改善體驗，不能作為授權機制。

## 九、現有系統差距

目前已有可保留的能力：

- 快速模板由後端固定覆寫為現在到三小時後。
- 已有單人同時使用數、每日次數、CPU、RAM、Disk 和 GPU 限制。
- 班級資源已具班級歸屬、控制政策及週期排程。
- 課程環境已具有多節點及版本概念。
- 範本克隆已有 linked clone 失敗後退回 full clone 的能力。

仍需修正的差距：

1. 現有快速模板主要以單一 VMRequest 為單位，尚未建立多機 PracticeSession。
2. 單人同時一個及每日三次目前可能按機器請求計算，必須改按 Session 計算。
3. 模板目錄的直接 clone 仍是另一條生命週期，學生可能繞過三小時規則。
4. 直接 clone 未必建立精確期限，可能形成長期存在的資源。
5. Resource 主要使用日期型 `expiry_date`，不足以作為三小時 Session 的權威期限。
6. 教學內容、操作腳本、提交成果與母機生命週期尚未完全分離。
7. 範本可見性主要仍是 private／global，缺少 class／users 等 Offering audience。
8. 尚未建立依整組規格與最大並行數進行的一次性版本審核。
9. 尚未完整處理已發布版本引用時禁止刪除底層模板。

## 十、建議實作順序

### P0：先阻止規則繞道

1. 學生禁止直接使用一般 `/templates/{id}/clone`；該 API 僅供教師／管理者，或內部轉入統一 PracticeSession 流程。
2. 學生入口全部改由 PracticeOffering 啟動。
3. 三小時期限由後端寫入精確 `expires_at`，前端只顯示伺服器回應。
4. 移除未真正套用至 LXC 的 Root 密碼欄位，避免錯誤安全期待。
5. 每個快速練習資源都必須能追溯到 Session、Offering、版本和 quota pool。

### P1：建立多機 Session 與容量治理

1. 建立 PracticeOffering、PracticeSession、PracticeSessionMachine。
2. 重用既有多節點課程環境版本作為 Blueprint，或建立可共用的 LabBlueprintVersion。
3. 建立整組容量及 IP 預留。
4. 將同時使用及每日次數限制改為 Session 維度。
5. 建立 `max_concurrent_sessions` 和 practice pool。
6. 補上全有或全無、失敗補建及整組回收。

### P2：版本審核與檔案治理

1. 建立官方／教師發布及一次性版本審核。
2. 建立 system、campus、class、users、private audience。
3. 建立 Content Bundle 及版本固定。
4. 建立學生成果提交／匯出。
5. 建立腳本能力白名單及高風險安全審核。

### P3：恢復與營運

1. 建立母模板引用保護及 deprecated／retired 狀態。
2. 建立 PVE 模板存在性對帳。
3. 建立 golden image 備份與恢復流程。
4. 建立到期通知、回收緩衝、失敗重試和管理者營運視圖。

## 十一、驗收標準

### 啟動與容量

1. 一個 Offering 可包含一至三台機器及固定拓樸。
2. 學生啟動一組三台環境只計為一次 Session。
3. 學生不能修改已核准的規格與三小時期限。
4. 容量或 IP 不足整組需求時，不建立任何節點。
5. 部分節點失敗可重試而不重複建立成功節點。
6. 達到 Offering 最大並行數時，後續學生不能繞過限制。

### 審核與授權

7. 官方 Offering 可直接發布。
8. 教師安全額度內版本可自動發布。
9. 超額、GPU、特權、公開網路或高風險腳本版本必須審核。
10. 已核准版本中的學生啟動不再逐次人工審核。
11. 非 audience 成員即使直接呼叫 API 也無法啟動。

### 三小時生命週期

12. 所有節點使用相同、由後端產生的 `expires_at`。
13. UI 明確顯示到期時間、倒數與回收政策。
14. 到期後整組停止並進入回收流程。
15. 回收可安全重試，不重複釋放 IP 或建立刪除工作。
16. Session 被回收後仍可查詢歷史、錯誤與提交成果。

### 檔案、腳本與刪除

17. 教學檔案及腳本具有 VM 外的版本化權威副本。
18. 學生必須保留的成果可在機器刪除前提交或匯出。
19. 高權限自動執行腳本未經允許或審核時不能發布。
20. 被已發布版本引用的母模板不能 hard delete。
21. PVE 母模板遺失時禁止新 Session 並產生警告。
22. 操作／腳本節點遺失時可依固定版本重建，不依賴原機保存教學內容。

## 十二、最終決策

本設計建議採用以下方向：

- 快速模板重新定義為一至三台機器的 PracticeOffering。
- 學生啟動維持免審核及固定三小時。
- 官方版本直接發布；教師版本在安全額度內自動發布，超額或高風險版本只審核一次。
- 教師指定誰能使用，但不能取代容量、最大並行數及安全治理。
- 多台機器必須是一個 PracticeSession，全有或全無、統一期限及整組回收。
- 三小時是不可編輯但必須透明顯示的後端政策，不是隱藏排程。
- 教學檔案、腳本與學生提交保存於 VM 外，學生機器回收不影響權威內容及成果。
- 已發布母模板採不可變版本、引用保護、棄用及備份恢復，不允許直接刪除。

此方向可以保留學生「點一下立即開始」的簡單體驗，同時控制教師高規格環境、大量並行啟動、三小時回收、腳本安全、母模板遺失及學生成果保存等風險。
