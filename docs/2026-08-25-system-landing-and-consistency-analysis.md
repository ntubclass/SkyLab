## 一、總結

Campus Cloud 的整體方向合理，具備實際落地條件。其核心可以整理為：

- 以「機器／運算資源」作為主要服務單位。
- 以「班級」作為正式教學與管理單位。
- 以「範本」提高環境重用性與教學部署效率。
- 以 AI 提供導覽、檢查與摘要，但不取代人員進行高風險決策。

目前的主要問題不是功能完全不存在，而是已完成的功能分散成數條彼此不一致的流程。學生個人申請、快速練習、範本複製、正式班級與公開課程各自有不同的審核、配額、生命週期和權限規則，尚未形成一致的「教師發布、學生取得、系統治理」閉環。

整體判斷如下：

| 評估面向 | 評價 | 說明 |
| --- | --- | --- |
| 概念合理性 | 8/10 | 角色與使用情境清楚，符合校園雲端教學需求。 |
| 功能完成度 | 7/10 | 個人申請、範本、班級批次配置、管理審核等基礎已存在。 |
| 學生與教師流程一致性 | 5/10 | 教師端具備正式班級功能，但學生端缺少對應入口與班級脈絡。 |
| 正式營運治理能力 | 5/10 | 權限、配額、排程、資源歸屬與生命週期仍需統一。 |

因此，系統可以繼續落地，但下一階段不宜只增加更多獨立功能；應優先統一資源配置流程、班級資源權責及學生與教師之間的操作鏈。

### 1.2 第二輪上線前稽核

- 修正 Worker 在 VM 建立後、成功狀態寫回前中斷可能造成的重複建機；補建會先找回並驗證既有資源。
- 刪除佇列新增「同一 VMID 只能有一筆進行中請求」的資料庫約束，支援多服務實例並行。
- 教師帳號若仍持有班級歷史會禁止刪除，避免班級與班級資源失去治理者。
- 即使班級關聯意外遺失，`allocation_scope=teaching_class` 的資源仍不會退化為學生個人資產，只允許管理者回收。
- 實際資料庫已升級至 `tc06_unique_active_delete`；原始錯誤查詢、外鍵刪除政策與唯一索引均已驗證。
- 相關核心測試 77 個通過；排除需 Redis／獨立測試資料庫的案例後，服務層測試 324 個通過，前端測試 133 個通過。

## 三、角色定位是否正確

### 3.1 學生

學生可：

- 申請個人機器。
- 在政策與配額允許範圍內調整自己的機器設定。
- 使用系統官方範本、校內公開範本或教師提供的學習範本。
- 使用教師配置給班級的練習機器。
- 透過 AI 取得操作導覽、設定建議及基本故障排除。

此定位合理，但「自己的機器」需要再區分：

1. **個人申請機器**：學生是資源持有人，可在政策內管理、調整與申請變更。
2. **班級配置機器**：應由班級或課程持有，學生只有使用權，不應自然取得刪除、延長或任意變更規格的完整權限。

學生可調整的範圍也應明確受政策限制，例如：

- 可選擇允許的作業系統或映像檔。
- 可在個人配額內調整 CPU、記憶體及磁碟。
- 可執行開機、關機、重設等被允許的操作。
- 可設定有限的網路或軟體選項。
- 不可繞過安全政策、網路隔離、稽核或管理者限制。

### 3.2 教師／導師

教師可：

- 申請個人工作機器。
- 建立與管理班級。
- 管理學生名單及課程期間。
- 為每位學生配置一台或多台練習機器。
- 建立機器範本、實驗環境及課堂內容。
- 將範本發布給指定班級、校內使用者或公開學習情境。
- 查看班級機器狀態，並透過 AI 協助檢查環境或異常。

此定位合理，但教師的「管理」應限定在其負責的班級、課程與內容，不能因為具有教師角色，就可修改其他教師的資料。

### 3.3 管理者

管理者不應只負責設備狀態檢查，還應負責整體平台治理：

- 審核個人與班級資源申請。
- 管理使用者、角色與權限。
- 設定個人、課程及班級配額。
- 管理平台容量、節點、IP 與資源健康狀態。
- 審查全校公開或官方範本的安全性。
- 處理資源到期、回收、異常與稽核。
- 使用 AI 產生每日營運摘要及待處理事項。

### 3.4 AI

AI 的定位應是輔助層，而不是獨立的權限角色：

| 使用者 | AI 適合提供的能力 |
| --- | --- |
| 學生 | 系統導覽、表單建議、資源選型、錯誤說明、基本故障排除。 |
| 教師 | 範本檢查、班級機器檢查、學生環境異常提示、教學活動摘要。 |
| 管理者 | 每日容量與設備摘要、異常彙整、待審核項目、風險與回收建議。 |

AI 可提出建議、草擬操作或整理資訊；涉及刪除資源、調整權限、批准大量資源、封鎖帳號等高影響行為時，仍應由人員確認並留下稽核紀錄。

## 四、合理且一致的目標流程

系統應清楚分成三條產品流程，三者共用同一套資源配置與治理核心。

### 4.1 個人資源

```text
學生／教師提出申請
        ↓
系統檢查政策與個人配額
        ↓
管理者審核（或符合條件時自動核准）
        ↓
統一配置服務建立機器
        ↓
使用者在允許範圍內管理與申請變更
        ↓
到期續用、停止或回收
```

### 4.2 公開練習

```text
教師建立範本／實驗藍圖／學習內容
        ↓
發布到指定可見範圍
        ↓
學生啟動短期練習
        ↓
系統以統一流程檢查配額、建立資源並記錄來源
        ↓
練習完成、逾時或主動歸還
        ↓
自動回收
```

### 4.3 正式班級

```text
管理者設定政策與班級配額
        ↓
教師建立課程版本、班級、名單、時段與教學內容
        ↓
教師選定機器範本或多機實驗環境
        ↓
管理者審核全班資源與容量
        ↓
系統建立「班級持有、學生使用」的資源配置
        ↓
學生從「我的班級」查看課程、檔案、時段與機器
        ↓
教師監看，AI 協助檢查與摘要
        ↓
課程結束後封存、續用或整批回收
```

## 五、現有功能的實際流程

目前程式中已存在數條可運作或接近可運作的流程：

| 現有流程 | 現況 | 一致性問題 |
| --- | --- | --- |
| 學生個人預約申請 | 經管理者審核後建立機器，流程相對完整。 | 可作為統一資源流程的基礎。 |
| 儀表板快速範本 | 建立自動核准的 VMRequest，提供約三小時的練習資源。 | 與直接複製範本的規則不同。 |
| 範本目錄直接複製 | 直接建立 TaskRecord 進行複製。 | 未走 VMRequest，預設到期、配額及審核規則不同。 |
| 正式教學班級 | 教師設定環境與名單，管理者審核後批次建立每位學生的多台資源。 | 教師端較完整，學生端缺少班級入口與脈絡。 |
| 公開學習路徑 | 教師發布任務、旗標與範本，學生可啟動短期實驗。 | 與正式班級及多機課程環境是兩套獨立模型。 |

## 六、學生與教師之間的主要流程斷點

### 6.1 教師建立了正式班級，但學生看不到完整班級體驗

正式班級功能目前偏向教師與管理者操作。學生雖可能取得批次配置的資源，卻缺少完整的「我的班級」流程，包括：

- 自己加入了哪些班級。
- 班級目前使用哪一版課程或實驗環境。
- 上課時間與可使用時段。
- 每週內容、教師上傳檔案與作業說明。
- 哪些機器屬於哪一門課，以及機器目前狀態。

這會造成教師認為已經完成開課與資源配置，學生卻只能在一般資源列表看到機器，無法理解其課程目的與時間限制。

相關位置：[teaching_classes.py](</D:/My Projects/Campus-Cloud/backend/app/api/routes/teaching_classes.py:268>)、[App.jsx](</D:/My Projects/Campus-Cloud/frontend/src/App.jsx:156>)。

### 6.2 班級週期排程與實際開關機機制未接通

班級批次配置將週期資訊記錄在 `BatchProvisionJob`，並直接建立 `Resource`；然而週期排程器主要查詢 `VMRequest`。手動啟動時段檢查同樣依賴最近一次核准的 `VMRequest`。

因此可能發生：

- 教師設定每週上課時段，但班級機器沒有依該時段自動啟動。
- 學生仍可能在班級規定時段之外啟動機器。
- UI 顯示有排程，但底層執行沒有同一份權威資料。

相關位置：[batch_provision_service.py](</D:/My Projects/Campus-Cloud/backend/app/services/vm/batch_provision_service.py:303>)、[recurrence_scheduler.py](</D:/My Projects/Campus-Cloud/backend/app/services/scheduling/recurrence_scheduler.py:70>)、[resource_service.py](</D:/My Projects/Campus-Cloud/backend/app/services/resource/resource_service.py:39>)。

### 6.3 班級機器被當成學生個人資產

批次建立的資源目前直接以學生作為 `Resource.user_id`。既有資源操作通常依擁有者判斷權限，因此學生可能取得與個人機器近似的控制能力，包括刪除或提出規格變更。

正式班級機器較合理的設計是：

- 所有權／治理權屬於班級或課程。
- 學生獲得限時使用權。
- 教師可進行課程範圍內的監看與教學控制。
- 管理者保留平台治理權。
- 刪除、延長、規格變更與課程結束回收由班級政策決定。

相關位置：[teaching_class.py](</D:/My Projects/Campus-Cloud/backend/app/models/teaching_class.py:13>)、[resources.py](</D:/My Projects/Campus-Cloud/backend/app/api/routes/resources.py:165>)。

### 6.4 班級機器消耗學生個人配額

全班申請預覽會檢查叢集容量與 IP，但批次工作建立每台機器時仍使用學生個人配額檢查。若部分學生已使用大量個人資源，可能出現「整班申請已批准，但部分學生配置失敗」的情況。

建議將配額至少分為：

- 個人申請配額。
- 公開練習短期配額。
- 正式班級配額。

若業務上確定要共用學生個人配額，也必須在送審前逐一預檢所有學生，不能等到批次執行時才部分失敗。

### 6.5 相同範本因入口不同而有不同規則

快速範本流程具備短期到期與頻率限制；範本目錄的直接複製則使用另一條服務流程，未必有相同的有效配額檢查、申請紀錄與預設到期時間。

這會使學生透過不同頁面啟動相同範本，卻得到不同權利與生命週期。所有入口應統一呼叫同一個 Allocation／Provision 流程，只以用途政策決定是否自動核准、期限和配額來源。

相關位置：[QuickTemplateFormPage.jsx](</D:/My Projects/Campus-Cloud/frontend/src/pages/personal/dashboard/QuickTemplateFormPage.jsx:170>)、[TemplateCloneDialog.jsx](</D:/My Projects/Campus-Cloud/frontend/src/pages/resource/templates/TemplateCloneDialog.jsx:28>)、[clone_service.py](</D:/My Projects/Campus-Cloud/backend/app/services/template/clone_service.py:58>)、[vm_request_service.py](</D:/My Projects/Campus-Cloud/backend/app/services/vm/vm_request_service.py:324>)。

### 6.6 正式課程與公開學習內容是兩套未連接的概念

目前存在兩組課程相關模型：

- `CourseEnvironment`：偏向一至多台機器、拓樸與版本化環境。
- `CoursePath`／`Room`：偏向任務、旗標、內容及學生自行啟動的實驗。

兩者缺少共同的課程實體與發布關係。公開學習路徑也偏向全域發布，難以自然限定到某個班級；同時內容流程主要綁定單一機器範本，無法完整承接正式課程的多機環境。

相關位置：[course_environment.py](</D:/My Projects/Campus-Cloud/backend/app/models/course_environment.py:21>)、[course.py](</D:/My Projects/Campus-Cloud/backend/app/models/course.py:34>)、[deployment_service.py](</D:/My Projects/Campus-Cloud/backend/app/services/course/deployment_service.py:145>)。

### 6.7 前端角色導覽及教師內容權限不一致

前端側邊欄主要只過濾部分管理者功能，學生仍可能看到教師或管理功能入口，點入後才由後端回傳 403。這不是安全漏洞本身，但會造成產品體驗混亂。

更重要的是，部分課程內容管理 API 只要求使用者具備教師角色，未持續驗證內容是否由該教師建立，因此可能讓教師修改、發布或刪除其他教師的課程內容。

建議同時處理：

- 前端依實際權限矩陣呈現功能，而非只判斷是否為管理者。
- 後端每個修改操作都驗證資源所有權、共同授課關係或明確授權。
- 列表、詳情與操作按鈕使用相同的權限判斷來源。

相關位置：[Sidebar.jsx](</D:/My Projects/Campus-Cloud/frontend/src/components/Sidebar/Sidebar.jsx:275>)、[permissions.py](</D:/My Projects/Campus-Cloud/backend/app/core/permissions.py:31>)、[course_admin.py](</D:/My Projects/Campus-Cloud/backend/app/api/routes/course_admin.py:31>)。

### 6.8 範本可見性不足以支援真實教學治理

範本目前主要是私有或全域公開，缺少下列範圍：

- 僅自己可見。
- 指定班級可見。
- 校內可見。
- 系統官方範本。

此外，課程環境的已發布列表偏向只列出教師自己的內容，不利共同授課或跨教師重用；建立課程環境時，也應確認所引用範本的所有權與可見性，而不只是確認 UUID 存在及類型正確。

相關位置：[course_environments.py](</D:/My Projects/Campus-Cloud/backend/app/api/routes/course_environments.py:291>)。

### 6.9 班級缺少完整結束與回收生命週期

雖然模型或介面已有封存狀態概念，但仍缺少完整的班級結束流程，例如：

- 結束或封存班級。
- 整批停止及回收班級機器。
- 延長指定班級或指定學生的資源。
- 修復批次配置中部分失敗的學生。
- 保留課程紀錄，但解除實際資源占用。

若沒有這一層，資源到期或被回收後，班級與資源映射容易殘留過期狀態。

### 6.10 LXC 密碼欄位的使用者預期與實際行為不同

快速 LXC 表單要求輸入密碼，但介面文字指出複製後仍使用範本原有憑證，輸入的密碼只保存在平台紀錄。這會讓學生誤以為密碼已套用至容器。

合理作法只有兩種：

1. 實際將密碼安全地套用到新建環境，並妥善處理機密資料。
2. 移除該欄位，改為清楚顯示範本登入方式或首次登入後變更流程。

### 6.11 班級名單缺少學生身分驗證

教師加入班級成員時，不應只確認帳號存在，還應驗證其具備學生身分，或有明確的跨角色加入政策。否則可能將教師或管理者錯誤加入學生名單，進而影響批次配置、配額及統計。

相關位置：[teaching_classes.py](</D:/My Projects/Campus-Cloud/backend/app/api/routes/teaching_classes.py:312>)。

## 七、目前值得保留的基礎

現有系統已有多項良好基礎，適合整理後繼續發展：

- 後端已有集中式角色權限矩陣。
- 班級與部分範本操作已有所有者檢查。
- 課程環境具備版本化及不可變版本概念。
- 管理者可審核班級批次資源，並預留叢集容量與 IP。
- 學生個人 VM 申請已具備審核、配置位置與到期概念。
- 課程部署流程已有重用 VMRequest 並彙整狀態的做法。
- 教師監看與廣播功能已有班級成員關係檢查。
- AI 已分別具備學生導覽、教師檢查及管理者監控的功能雛形。

這些能力不需要推翻，重點是讓它們建立在同一套權威資料與資源生命週期上。

## 八、建議統一的領域模型

為避免「範本、課程、班級、部署」名稱彼此重疊，建議將核心概念固定如下：

| 建議名稱 | 責任 |
| --- | --- |
| `MachineTemplate` | 一台 VM 或 LXC 的可重用來源。 |
| `LabBlueprint`／`CourseEnvironment` | 一至多台機器、網路拓樸及版本。 |
| `CourseContent` | 任務、旗標、教材、每週內容及檔案。 |
| `ClassOffering`／`TeachingClass` | 實際開課班級、名單、時段及鎖定的內容／環境版本。 |
| `ResourceAllocation`／`ResourceGrant` | 機器為何存在、由誰治理、誰可操作、使用期限、配額來源及控制政策。 |

其中 `ResourceAllocation` 是統一流程的關鍵。每台建立出的資源至少應能回答：

- 來源是個人申請、快速練習、公開課程還是正式班級。
- 治理者是個人、班級、教師還是管理者。
- 哪位使用者目前具有使用權。
- 使用哪一個配額池。
- 何時開始、何時到期、是否允許續用。
- 允許哪些控制操作。
- 對應哪一筆申請、班級、課程版本或批次工作。

## 九、建議落地優先順序

### P0：先修正流程與權責一致性

1. **增加資源來源及治理資訊**

   至少加入 `origin`、`teaching_class_id`、`control_policy`、`expires_at` 等欄位或等價關聯，並將正式班級資源改為班級持有、學生使用。

2. **統一所有資源建立入口**

   快速範本、直接複製、公開課程與正式班級都應進入同一個 Allocation／Provision 核心，統一處理申請紀錄、配額、到期、稽核、狀態與失敗補償。

3. **接通正式班級排程**

   每筆班級資源必須連結可被排程器辨識的配置／申請，或讓排程器直接以班級批次工作作為權威來源；開機權限檢查也必須讀取同一份時段政策。

4. **建立學生「我的班級」**

   增加學生唯讀 API 與頁面，顯示班級、時段、每週內容、教師檔案、已配置機器及操作限制。

5. **統一前後端權限**

   前端導覽依權限顯示；後端補齊教師內容所有權、共同授課與發布範圍檢查。

### P1：補齊營運與教學治理

6. 分離個人、短期練習與班級配額，或在送審前完成逐一學生預檢。
7. 增加班級結束、封存、整批回收、續用與部分失敗修復流程。
8. 將範本可見性擴充為私有、班級、校內及系統官方。
9. 移除無實際效果的 LXC 密碼欄位，或完成安全的密碼套用機制。
10. 加入班級成員角色驗證、邀請／加入通知及名單異動稽核。

### P2：再強化 AI 與分析能力

在 P0、P1 的資料與流程一致後，再讓 AI 讀取統一資料：

- 學生 AI：依班級、機器來源、時段及錯誤狀態提供精確導覽。
- 教師 AI：依課程版本、班級資源與學生異常產生檢查報告。
- 管理者 AI：依配額、容量、排程、失敗工作及待回收資源產生每日摘要。

若底層資料仍分散，AI 只能分別解讀不同流程，容易給出互相矛盾的建議，因此 AI 擴充應排在核心一致性之後。

## 十、驗收標準

完成上述重整後，可用以下情境驗證系統是否真正一致：

1. 教師建立班級、選擇課程版本、加入學生、設定每週時段並送出資源申請。
2. 管理者能在一次審核中看到全班所需的 CPU、記憶體、磁碟及 IP，且核准前不會出現未知的個人配額衝突。
3. 系統為所有學生建立具班級來源、使用期限及控制政策的資源；部分失敗時可重試而不重複建立。
4. 學生在「我的班級」看到課程內容、教師檔案、上課時段及對應機器，不需自行猜測資源用途。
5. 學生不能刪除班級持有的機器，也不能在禁止時段啟動；個人機器則依個人政策操作。
6. 教師只能管理自己的班級或已獲授權的共同授課班級，不能修改其他教師內容。
7. 課程結束後，教師或管理者可一次封存班級並回收資源，班級歷史仍可查詢。
8. 不論學生從快速入口、範本目錄或課程頁面啟動資源，底層都有一致的配置紀錄、配額、期限與稽核資訊。

## 十二、最終結論

系統的角色想法與校園教學情境是正確的，也已有相當多可沿用的功能。真正需要優先處理的是「一台機器究竟屬於誰、為何建立、使用多久、由哪個配額支付，以及學生和教師各能做什麼」。

只要先完成統一資源配置、班級資源使用權、學生班級入口、排程接通及權限補強，學生、教師與管理者三方流程就能形成一致且可治理的閉環；AI 也才能建立在可靠資料上，提供真正有用的導覽、檢查與日常摘要。


核心缺少 6 條流程：
1. 學生接收課程流程
   教師建立班級 → 加入學生 → 學生「我的班級」→ 查看教材、時段、課程機器。
   目前學生端幾乎沒接上。
2. 班級機器權限流程
   班級持有機器 → 學生限時使用 → 教師管理 → 管理者治理。
   目前班級機器被當成學生個人機器。
3. 統一機器建立流程
   個人申請／快速練習／範本複製／班級配置 → 統一檢查配額、期限、權限與稽核。
   目前各入口走不同規則。
4. 班級排程執行流程
   教師設定上課時間 → 系統自動開關機 → 限制學生非上課時段操作。
   目前排程資料與實際控制沒有接通。
5. 班級配額與批次失敗處理
   送審前檢查全班資源 → 核准 → 全部建立 → 失敗可重試。
   目前可能核准後才因學生個人配額不足而部分失敗。
6. 課程結束流程
   課程結束 → 停止機器 → 整批回收 → 封存班級 → 保留紀錄。
   目前缺少完整的結束、回收、續用與修復流程。
最核心的是：學生班級入口、班級機器權責、統一資源建立、排程真正執行。


模板練習主要缺少 5 條核心流程：
1. 統一啟動流程
   選擇模板 → 檢查權限與配額 → 建立練習機 → 設定期限 → 留下紀錄。
   目前「快速模板」和「直接複製模板」走不同規則。
2. 自動回收流程
   啟動練習 → 顯示剩餘時間 → 到期提醒 → 延長或歸還 → 自動刪除。
   目前部分模板複製沒有明確期限，容易留下長期資源。
3. 模板發布與可見範圍
   教師建立 → 測試 → 發布到指定班級／全校 → 必要時管理者審核。
   目前主要只有私有或全域公開，缺少班級範圍。
4. 模板與課程內容連接
   模板／多機環境 → 教師題目與教材 → 學生啟動 → 完成練習 → 保存結果。
   目前機器模板、正式課程環境、任務／旗標是分散的系統。
5. 練習結果流程
   學生完成練習 → 提交答案或狀態 → 教師查看結果 → AI 協助檢查。
   目前偏向「把機器建立出來」，缺少完整的完成、提交與教師追蹤閉環。
